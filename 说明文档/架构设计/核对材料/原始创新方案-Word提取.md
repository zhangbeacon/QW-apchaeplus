**P004** 0. 摘要

**P005** 同构部署使同一缺陷在多台服务器上被同一攻击重复命中。本作品以 Apache httpd 2.4.49 为基准程序 V1，构建一条自动化异构变体生成与验证流水线：生成两个功能等价、内部实现与运行形态不同的变体 V2/V3，并用同一套触发脚本在 V1/V2/V3 上对比 6 个独立根因漏洞的攻击表现，以"原语级差异指纹"输出机器可判定的安全增益证据。

**P006** 与常见做法的区别：我们不是"选两个编译参数直接编译"，而是先用 11 个 CVE 的实测数据回答"什么差异对什么漏洞有效"，再按漏洞类型分派异构手段；每个测试自带阳性（漏洞版必中）与阴性（修复版必不中）双向对照；全部结论由退出码/响应特征/崩溃信号等机器可判定证据支撑。流水线另设常驻 LLM 监管 Agent，对构建失败、资源异常与证据完整性进行实时诊断与处置，全程决策留痕可审计。

**P007** 当前实测基础：11 个 CVE 中 10 个已在 2.4.49 未修复版复现成功（1 个静态定位），覆盖 7 类 CWE；Ubuntu 2.4.52 修复版负向对照全部通过；全部测试可一键复跑。

**P008** 1. 题目理解与目标

**P009** 1.1 赛题核心问题

**P010** 三个版本不能只是文件名或哈希不同——必须存在影响攻击过程的安全相关差异，且该差异可被主办方复核。赛题对"差异"的定义原文即要求到利用原语粒度（"攻击利用的原语、控制流结果、信息泄露程度或最终攻击目标不同"），这决定了本作品的证据体系必须做到原语级量化。

**P011** 1.2 目标

**P012** V1 选型钉定在漏洞密度最高的历史版本（已完成：2.4.49）；

**P013** 自动化流水线生成 V2/V3（第二阶段实施）；

**P014** 对 6 个独立根因漏洞跑同一触发脚本，产出三态差异矩阵；

**P015** 量化安全增益与开销，输出可复核的安全增益报告。

**P017** 2. 基准程序选择与威胁模型

**P018** 2.1 选型方法与结果

**P019** 选型经三重独立验证：① 三份独立选型报告交叉筛选（各推第一名：nginx / dnsmasq / Apache）；② 三个"第一名"软件全部完成复现实测（共 10 个 CVE，9 个成功）后按证据强度终选；③ 三个 AI 评审模型独立审计并两轮表决（3:0）。

**P020** 终选结果：Apache httpd 2.4.49。 决定性理由：

**P021** CVE-2021-41773 是候选池中唯一不依赖 sanitizer、单条 HTTP 请求即可实测的 RCE（远程、在野利用、CISA KEV 收录）；

**P022** 逻辑型漏洞占优，V1/V2/V3 差异可直接呈现在 HTTP 状态码/响应层（200 vs 400/500/崩溃），满足赛题"差异不能只是哈希/地址不同"的要求；

**P023** 模块体系（proxy/rewrite/lua/sed/cgi）提供丰富的可配置攻击面，便于构造多样化测试例。

**P024** 落选说明（有实测依据）：nginx 两条内存缺陷仅 ASAN 可见，差分观察面窄；dnsmasq 两条核心漏洞仅 ASAN 可见且 13704 需重钉 2.77 版本，答辩口径风险大。

**P029** 2.3 威胁模型与实验边界

**P030** 攻击者可向 HTTP 端口提交受控请求（含路径、头、body、代理 URI），目标为文件泄露/命令执行/请求走私/SSRF/DoS。所有测试在本机隔离 WSL 环境完成，载荷无害化（id/uname、标记字符串）。运行配置差异（如 Require all granted、ProxyRequests On、mod_lua 启用）作为变体组成部分如实记录，不冒充编译差异。

**P047** 3.2 创新点一：漏洞类型分派的异构策略（Type-Aware Diversification）

**P048** 依据（实测）：对 11 个 CVE 的挖掘与复现表明，漏洞对异构手段的敏感性呈两极：

## 表格 T03
**T03R01** 漏洞类型 | 实例 | 对编译器/分配器 | 对源码级等价重构 | 对配置收敛

**T03R02** 逻辑型（路径穿越/走私/SSRF） | 41773、44224、22720、25690 | 不敏感（换 gcc/clang 仍命中） | 敏感（规范化重写即失效） | 敏感（关代理/收紧授权即失效）

**T03R03** 内存型（越界写/下溢/未初始化） | 44790、23017、14491 | 敏感（堆布局漂移 → 崩溃/静默/泄露三态） | 部分敏感 | 不适用

**P049** 分派规则：V2 采用加固型编译栈（clang + FORTIFY + 分配器替换），针对内存型漏洞制造"崩溃 vs 静默"漂移；V3 采用语义等价重构 + 攻击面收敛（路径规范化等价实现、代理/CGI 配置最小化），针对逻辑型漏洞使触发失效。V1 为原始基线。

**P050** 与赛题的对齐：满足"变换层次、技术原理和方法组合合理"，且分派依据是 11 个 CVE 的实测数据（总报告 §7 敏感性表），不是经验假设。

**P051** 3.3 创新点二：在线拟态裁决网关（第二阶段实施）

**P052** 在 V1/V2/V3 前增加一层动态调度 + 响应表决网关：请求按种子轮换分发到某个变体实例；网关对响应做归一化（抹除 Date/Server 等非语义字段）后比对，异常响应被表决丢弃。

**P053** 功能等价自动证明：正常流量下三变体响应归一化后一致，等价性由网关在线保证而非人工断言；

**P054** 攻击抑制演示：41773 直打 V1 泄露 /etc/passwd，经网关分发时仅命中有漏洞变体时成功，命中加固变体即被拦——"单点被攻破，系统仍安全"；

**P055** 与赛题对齐："运行时选择、隔离策略的差异"是赛题明列的攻击链多样化手段；

**P056** 边界声明：裁决网关是部署层增强，不改变单变体漏洞存在性——正好对应赛题要求的"漏洞仍存在但利用受抑制 vs 漏洞已消除"区分。

**P057** 3.4 创新点三：原语级差异指纹与证据卡

**P058** 每个漏洞 × 每个变体输出一张原语指纹卡，量化记录：

**P060** 3.5 创新点四：证据链即代码（Evidence-as-Code）

**P061** 每个 verify.sh 退出码即结论；报告结论绑定机器可判定断言；

**P062** 防陈旧证据守卫：二进制缺失即失败、旧证据先删后跑、PASS 必须来自本轮新鲜输出（mtime 校验）——该机制来自实测中抓到并修复的"旧文件误判 PASS"问题；

**P063** 负向对照内建：每次判定自带阳性对照（漏洞版必中）与阴性对照（修复版必不中，Ubuntu 2.4.52 / 上游补丁版）；

**P064** 一条命令重建全部证据并 diff 结论漂移。

**P065** 3.6 创新点五：LLM 监管 Agent——执行/监管/裁决三层分离

**P066** 自动化流水线的痛点不是"没脚本"，而是脚本失败时没人管：构建报错、资源超限、证据文件异常、多任务抢端口——这些恰是评审现场最容易翻车的环节。本设计在流水线中引入常驻 LLM 监管 Agent，形成"执行层（确定性脚本）—监管层（LLM 诊断与处置）—裁决层（机器判定门）"三层架构。

**P068** 三条铁律（防幻觉设计）：

**P069** 监管 Agent 只有处置建议权，没有判定权——漏洞命中与否、变体是否等价，永远由机器判定门（退出码/回放验证/负向对照）说了算；

**P070** 每个决定写入 journal.jsonl 决策日志（时间、依据、动作、回滚点），全程可审计；

**P071** 任何修改先存快照，改砸可回滚。

**P072** 实现要点：事件监听循环（构建/测试/采证的失败与异常事件）→ LLM 诊断（可用本机 GPUStack 模型，成本≈0）→ 工具调用执行处置；判定类事件不走 LLM，直接机器判定。

**P073** 3.7 校准/留出划分

**P074** 6 个计分 CVE 按根因分为校准集（41773/44790/22720）与留出集（44224/38474/25690）：变体配对只依据校准集选择，留出集仅做最终验证——避免选择过程过拟合，这是多数仅有 3 个漏洞的队伍无法实施的验证纪律。
